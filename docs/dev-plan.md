## MVP 범위

| 기능 | 완료 기준 |
|---|---|
| 영상 → 레시피 | 숏츠 링크(또는 영상 파일)로 요리명·재료·원문 분량·조리 순서 생성, 항목별 근거, 미확인 분량 표시, 처리 상태·실패·재시도 |
| 확인·수정 | 결과 수정 후 저장, 수정 전 추출 결과와 수정본을 함께 보관 |
| 내 레시피북 | 사용자별 목록·상세·수정·삭제 |
| 품질 개선 루프 | 고정 평가셋, 평가 지표 자동 계산, 기본 버전과 파인튜닝 버전 비교 |

냉장고 인식·요리 에이전트·재고·단위 환산 등은 기획안의 보류 메모를 따른다.

### 추출 파이프라인 (수빈)

각 단계는 결과를 파일로 저장하고 버전을 남긴다. 그래야 영상을 다시 받지 않고 뒤 단계만 다시 돌리며 실험할 수 있다.

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| 1. 수집 | 링크 → 영상·오디오·제목·설명 | 원본 파일, 메타데이터 |
| 2. 음성 인식 | 오디오 → 시각이 붙은 자막 | transcript |
| 3. 화면 텍스트 | 프레임 추출 → OCR(자막·재료 표기) | ocr |
| 4. 근거 묶음 | 설명·음성·화면 텍스트를 시각 순으로 합침 | **evidence bundle** |
| 5. 구조화 | 근거 묶음 → 레시피 JSON(항목별 근거 포함) | recipe draft |
| 6. 정규화·검증 | 재료 키 매핑, 분량 파싱, 스키마·규칙 검증 | 최종 RecipeDraft |

- 파인튜닝 대상은 **5단계 구조화 모델**이다. 1~4단계는 기존 도구를 쓰고 필요할 때만 교체한다.
- 실행마다 run_id와 단계별 버전(모델·프롬프트·설정)을 기록한다.
- 워커의 `process_video_recipe`가 이 파이프라인을 호출한다. 출력은 `schemas/recipe.schema.json`(RecipeDraft)을 따르고, 근거 필드가 필요하면 계약을 먼저 바꾼 뒤 구현한다.

### 정답 데이터·평가·파인튜닝 루프 (선규)

- **학습 예제 = (evidence bundle, 정답 레시피 JSON).** 수빈과 선규의 경계는 evidence bundle 스키마다. 1주차에 함께 확정한다.
- **정답 만들기:** 강한 모델이 초안을 만들고 사람이 영상을 보며 고친다. 라벨링 가이드(분량 표기, 미확인 판단, 재료 이름 규칙)를 먼저 정한다.
- **데이터 분할:** 영상 단위로 학습·평가를 나눈다. 평가셋은 고정하고 학습에 절대 쓰지 않는다.
- **지표:** 재료 재현율·정밀도, 분량 정확도, 근거 없는 분량(지어낸 값) 수, 조리 순서 누락, 스키마 통과율.
- **파인튜닝 방식:** 1주차에 비용·데이터 반출 조건을 보고 정한다. 후보는 API 파인튜닝과 오픈 모델 LoRA다. 정답 데이터가 적을 때는 프롬프트 개선과 비교해 실제로 나아졌는지 확인한다.
- 사용자 수정본(수정 전/후 쌍)은 검토를 거쳐 학습 데이터 후보로 쓴다.

### 화면 (유란)

링크 입력 → 진행 상태 → 레시피 확인(근거·미확인 표시) → 수정 → 레시피북 목록·상세. 수정 화면은 사용자가 쉽게 고칠 수 있어야 데이터도 쌓이므로 핵심 화면으로 다룬다.

## GitHub 협업·병합 규칙

저장소: https://github.com/pbl-applied-ai/applied-ai (Public)

| 항목 | 규칙 |
|---|---|
| main 반영 | 기능 브랜치 → PR → 작성자 외 팀원 1명 승인 → check 통과 → Squash merge |
| main 직접 push·강제 push·삭제 | 하지 않음 |
| 승인 후 중요한 변경 | 리뷰어에게 알리고 다시 확인받음 |

- 위 규칙은 main Ruleset("main 보호")으로 GitHub가 강제한다: PR 필수, 승인 1명, `check` 통과, 강제 push·삭제 금지, 예외 없음.
- `.github/CODEOWNERS`로 리뷰어가 자동 지정된다.
- 지금 CI는 `check`(스키마·예시 검사)뿐이다. pgtap은 레시피북 DB가 생길 때 추가한다.
- 레포가 Public이므로 API 키·`.env`는 커밋하지 않는다. 영상에서 뽑은 텍스트(정답 데이터)도 공개된다는 점을 감안한다.

매일 최신 main에서 기능 브랜치를 만든다. 예: feat/pipeline-ingest, feat/eval-harness, feat/recipe-book-ui. PR에는 변경 내용·실행/검증 결과·미완성 항목을 적는다. Claude는 구현·자체 검증·PR 초안 작성을 지원하고 팀원의 Approve를 대신하지 않는다.

## 검증·범위 조절

- 매주 평가셋 점수를 갱신하고 이전 점수와 비교한다. 점수가 떨어지는 변경은 이유를 적고 병합한다.
- 평가셋 영상으로 과적합하지 않도록 평가셋 결과를 보고 프롬프트·데이터를 직접 고치지 않는다. 오류 분석은 별도 개발용 영상으로 한다.
- 지연 시 화면 장식·지원 입력 범위를 먼저 줄인다. 링크 → 레시피 → 레시피북 흐름과 평가 비교는 유지한다.
- 11/20 이후 새 기능은 넣지 않는다.
