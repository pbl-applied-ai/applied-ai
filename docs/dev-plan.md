# 숏폼 레시피 서비스 개발 계획 v0.8

수정일: 2026-10-22 · 팀 리뷰용
변경: MVP 화면을 링크 입력 → 레시피 확인·수정 → 저장 → 내 레시피북으로 단순화. 항목별 근거·출처·시각 이동 UI와 신뢰도 요약을 제외하고, 내부 근거 데이터·분량 검증·평가는 유지. 분량 검증 버그는 수빈이 담당.
관련 문서: [기획안](<plan.md>) · [UX 플로우](ux-flow.md) · [경쟁 서비스 비교](<competitors.md>)

## 목표와 일정

## MVP 범위

| 기능 | 완료 기준 |
|---|---|
| 영상 → 레시피 | Shorts 링크(또는 영상 파일)로 요리명·재료·원문 분량·조리 순서 생성, 확인되지 않은 분량은 빈칸으로 제공, 처리 단계 표시·실패 종류별 안내·재시도 |
| 확인·수정 | 결과 수정 후 저장. 추출 결과는 그대로 두고 사용자 레시피를 따로 저장. 고친 항목은 "직접 입력" 표시 |
| 내 레시피북 | 사용자별 목록·상세·수정·삭제 |
| 품질 개선 루프 | 고정 평가셋, 평가 지표 자동 계산, 기본 버전과 파인튜닝 버전 비교 |
| Instagram 릴스 (조건부) | 캡션·미디어 확보를 먼저 검증한 범위만 지원. 캡션만 확보하면 설명 기반 결과로 표시하고, 읽을 근거가 없으면 업로드 안내. 일정이 밀리면 먼저 뺀다 |

**화면 범위:** 결과 화면은 요리명·재료·원문 분량·조리 순서와 수정·저장에 집중한다. 항목별 근거 버튼·원문·출처·시각 이동 및 신뢰도 요약은 MVP에서 제외한다. 근거 데이터·시각·검증 상태는 내부 검증·평가·파인튜닝을 위해 유지하며, 확인되지 않은 분량은 추측하지 않고 비운다.

냉장고 인식·요리 에이전트·재고·단위 환산 등은 [기획안](<plan.md>)의 보류 메모를 따른다.

**작업 순서:** 이전 PR 반영 → 수빈의 분량 검증 버그 수정 → YouTube 동작을 유지하며 수집기 경계 분리 → Instagram 수집 후보 검증 → 지원 가능한 입력만 연결. 분량 검증 버그는 수빈이 담당하고 선규에게 공유해 수정 중복을 방지한다. 기존 버그와 플랫폼 기능 추가는 별도 PR로 나눈다.

현재 후처리는 `12스푼` 근거에서 `2스푼`을 부분 일치로 확인하거나, 같은 구간의 다른 재료 분량을 잘못 붙여도 확인으로 처리할 수 있다. 숫자 경계와 해당 재료·분량의 연결을 검증하고 불명확하면 내부 상태를 검토 필요로 남기고 화면 분량은 비우는 회귀 검사를 추가한다.

### 추출 파이프라인 (수빈)

단계별 산출물과 버전을 분리해 뒤 단계만 다시 실행할 수 있게 한다. 개발·평가 자료는 비공개 저장소에 보관한다. 일반 사용자의 원본 미디어는 처리·재시도에 필요한 임시 보관만 하고 삭제한다. 보관 기간과 삭제 기준은 #3에서 정한다.

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| 1. 수집 | 플랫폼별 수집기: 확보 가능한 캡션·시간 있는 자막·제목·미디어 참조·댓글과 누락 이유 반환 | 공통 수집 결과, 임시 미디어 |
| 2. 음성 인식 | 시간 있는 자막 우선 재사용. 필요 시 확보한 음성·영상에서 시각이 붙은 전사 생성 | transcript 또는 미실행 이유 |
| 3. 화면 텍스트 | 영상이 있고 화면 근거가 필요한 입력에서 프레임 추출 → OCR, 시각 포함 | ocr 또는 미실행 이유 |
| 4. 근거 묶음 | 확보한 설명·댓글·자막/음성·화면 텍스트를 출처와 구간 ID가 있는 목록으로 합침 | **evidence bundle** |
| 5. 구조화 | 근거 묶음 → 레시피 JSON. 항목마다 근거 구간 ID 인용, 분량은 원문 그대로 | recipe draft |
| 6. 정규화·검증 | 구간 ID 검증, 시각 계산, 분량 파싱, 스키마·규칙 검증 | 최종 RecipeDraft |

**1단계 — 플랫폼별 수집기.** `collectYouTube`, `collectUpload`, `collectInstagram`(조건부)는 플랫폼 전용 수집만 담당하고 이후에는 공통 입력을 사용한다. 원본 영상 링크 처리는 별도 플랫폼 어댑터로 분리하며 항목별 시각 이동 UI는 MVP에서 구현하지 않는다. 임베드나 oEmbed가 표시된다고 분석용 원본 미디어를 확보했다고 판단하지 않는다.

공통 수집 결과 계약은 #3에서 아래 필드를 합의한다. **모든 입력에 영상·오디오·캡션·댓글이 있다고 가정하지 않는다.**

| 필드 묶음 | 요구 사항 |
|---|---|
| 원본 식별 | `platform`, `source_id`, `source_url`, 제목·작성자, 수집 시각·수집기 버전 |
| 설명·캡션 | 실제 확보한 원문과 출처. 없으면 빈 결과와 누락 이유 |
| 자막·전사 | `text`, `start_ms`, `end_ms`, 생성 방식(플랫폼 자막/ASR)·도구 버전. 시각 없는 텍스트는 구분 |
| 미디어 참조 | 임시 파일 또는 접근 가능한 참조, 형식·길이·만료 정보. URL 존재와 실제 다운로드·디코딩 성공을 분리 |
| 댓글 | 확보한 경우에만 원문·출처·고정 여부. 댓글 수집은 MVP 필수 성공 조건이 아님 |
| 수집 상태 | 항목별 `available` / `missing` / `failed`, 실패 이유·재시도 가능 여부·처리 시간·수집 비용 |

시간 없는 캡션·설명·전사 원문에는 가짜 시각을 붙이지 않는다. 캡션은 `description` 근거로 매핑한다. 시각 없는 음성 전사를 보존할 상태는 스키마 합의 후 추가하며, 현재 계약이 시간 없는 `asr`를 허용한다고 가정하지 않는다. 기존 `S01`·`D01` 내부 ID와 팀 스키마 `asr-0`·`desc-0`의 대응도 어댑터에서 관리한다.

**2~3단계 — 확보한 입력에 따라 실행.** 시간 있는 자막이 있으면 불필요한 ASR을 건너뛴다. 자막이 없거나 필요한 내용이 부족하고 음성에 접근할 수 있으면 ASR을 실행한다. 영상이 없으면 OCR을 성공으로 표시하지 않는다. 도구가 없거나 실패하면 그 사실을 근거 범위에 남긴다. 캡션만 있어도 근거가 충분하면 시각 없는 레시피를 만들 수 있고, 부족하면 부분 결과 또는 업로드 안내를 제공한다. 전사 텍스트만 반환하는 서비스는 내부 시각 평가 가능 여부를 별도로 확인한다.

**5단계 — 근거 인용.** 근거 묶음은 `[S12 00:41] 고추장 두 스푼…`처럼 구간 ID와 시각을 붙여 모델에 넣는다. 모델은 시각을 직접 쓰지 않고 `S12` 같은 구간 ID만 인용한다. 분량은 근거 원문에 나온 표현 그대로 쓰고, 근거가 없으면 비운다. 요리 영상이 아니라고 판단하면 `not_a_recipe`로 표시한다.

**6단계 — 결정적 후처리.** 아래는 모델이 아니라 코드가 한다.

- 인용한 구간 ID가 실제로 있는지 확인한다. 없으면 그 근거를 버리고, 근거가 남지 않은 분량은 미확인으로 바꾼다.
- 항목 시각 = 인용한 근거 중 시각이 있는 구간의 가장 이른 시작 시각. 모두 시각이 없으면 null이다. 시각은 내부 검증·평가용으로만 유지하고 MVP 화면에는 시각 이동 기능을 제공하지 않는다.
- 분량 원문을 수량·단위로 파싱해 별도 필드에 둔다. 화면에는 원문을 보여 주고, 파싱 결과는 검증과 평가에만 쓴다.
- 부분 일치만으로 분량을 확인 처리하지 않는다. 숫자·단위 경계와 해당 재료의 문맥을 검증하고 불명확하면 내부 검토 필요 상태로 남기고 화면 분량은 비운다. 설명이 부족해도 요리명·해시태그만으로 분량을 채우지 않는다.
- 같은 재료에 출처끼리 다른 분량이 있으면 내부 충돌 상태로 기록한다(선택 기능). [#3 대기]

**공통.**

- 파인튜닝 대상은 **5단계 구조화 모델**이다. 1~4단계는 기존 도구를 쓰고 필요할 때만 교체한다.
- 실행마다 run_id와 단계별 버전(모델·프롬프트·설정), **처리 시간과 모델 호출 비용**을 기록한다. 4주차 비용·속도 점검과 발표 비교에 그대로 쓴다. 참고 기준: 경쟁 서비스 한 곳에서 Shorts 한 편이 약 16초 걸렸다(1건 관찰).
- 워커의 `process_video_recipe`가 이 파이프라인을 호출하고, 출력은 `schemas/recipe.schema.json`(RecipeDraft)을 따른다. 스키마를 바꿀 때는 계약을 먼저 바꾼 뒤 구현한다.

### Instagram 수집 검증과 지원 결정

[경쟁사 공식 안내](<competitors.md#instagram-구현-조사>)는 설명·음성·화면 정보의 활용을 설명하지만 실제 수집 방법은 알려주지 않는다. 수집·전사·생성의 분리는 우리 설계 제안이다. **영상 주소 확보 업체·라이브러리는 네 서비스 모두 미확인**이므로 구현 후보를 확보했다고 계획하지 않는다. 아래 기준은 우리 검증을 위한 제안이며 경쟁사 성능 수치가 아니다.

1. **1주차 사전 검증:** 공개·사용 권한이 있는 개발용 릴스 12개를 캡션 중심/음성 중심/화면 글자 중심/혼합 각 3개로 구성한다. 평가셋·학습셋·경쟁사 비교 세트와 분리한다. YouTube의 끝까지 동작하는 흐름을 우선하며 사전 검증은 최대 2인일로 제한한다.
2. **후보 확인:** 자체 공개 정보 수집과 계약 가능한 외부 수집 서비스 등을 조사하되 사용 조건·비용·출처·보관 정책을 확인한다. 경쟁사 서버를 우리 수집기로 호출하거나 개인 계정 쿠키로 제한을 우회하는 방법은 후보에 넣지 않는다. 구체적 후보·비용은 미정이다. 실험 전에 확보율·비용·지연 시간의 통과 기준을 팀에서 정해 기록한다.
3. **반복 확인:** 가능한 후보로 같은 세트를 다른 날 2회 실행해 캡션 확보율, 영상/음성 실제 접근·디코딩 성공률, 시간 있는 전사 가능률, 실패 이유·시간·편당 비용을 분리 기록한다. URL 반환만으로 성공 처리하지 않는다. 비공개·삭제·지원 안 함은 별도 실패 fixture로 검증한다.
4. **지원 결정:** 10/27에 결과와 사전 합의한 품질·비용 기준으로 `미지원` / `캡션 기반 제한 지원` / `음성·영상 포함 지원 후보`를 결정한다. 두 차례 기록·후단 사용 가능성·실패 시 대안이 없으면 연결을 보류한다. 유리한 사례만 골라 지원 완료로 발표하지 않는다.
5. **연결 조건:** 3주차에 후보를 연결하더라도 출시 전 레시피 품질·근거·실패 UX를 확인한다. 캡션만 읽은 결과는 설명 기반이라고 표시하며 영상 분석으로 부르지 않는다. 캡션이 부족하고 음성·화면도 확보 못 하면 내용을 생성하지 않고 업로드를 안내한다.

### jobs (수빈·선규 공동)

| 필드 | 내용 |
|---|---|
| `canonical_key` | 플랫폼 + 영상 ID (예: `youtube:<id>`). 같은 키와 같은 추출기 버전의 성공 결과가 있으면 다시 처리하지 않고 재사용 |
| `stage` | 수집 → 필요 시 음성 → 필요 시 화면 글자 → 정리. 실제 실행 단계만 표시하고 미실행 단계와 이유를 기록 |
| `status` | 대기 · 처리 중 · 성공 · 실패 |
| `error_code` | `retryable`(시간 초과·일시 오류) / `unavailable`(열 수 없음·비공개·삭제) / `unsupported_source` / `not_a_recipe` / `insufficient`(정보 부족) / `schema_error` |
| `run_id` | 성공 시 추출 결과 연결 |

`error_code`는 UX 플로우의 실패 안내와 1:1로 맞춘다. `retryable`은 다시 시도, `unavailable`·`unsupported_source`는 파일 업로드 안내, `not_a_recipe`는 다른 영상 안내, `insufficient`는 찾은 만큼 보기. 동시에 진행 가능한 작업 수(여러 개 허용 여부)는 #3에서 정한다. [#3 대기]

항목별 수집 상태는 전체 job 실패와 구분한다. 영상 접근에 실패해도 유효한 캡션 근거가 남으면 제한된 결과를 반환할 수 있다. 재시도 횟수는 제한하고 미디어 참조가 만료됐으면 수집 단계부터 갱신한다. 캐시 재사용 시 확보한 출처·수집 버전·내용 변경/만료 여부를 확인하고, 나중에 더 완전한 출처를 확보할 기회를 막지 않는다.

### 레시피 저장 구조 (선규)

- **추출 결과(run)는 절대 고치지 않는다.** 같은 영상을 쓰는 사용자들이 공유하고, 평가와 학습의 기준이 된다.
- **사용자 레시피는 추출 결과를 참조하는 사본이다.** 저장할 때 추출 결과의 재료·단계를 복사하되 **항목 ID를 그대로 유지**한다. 그래야 고치지 않은 항목의 근거가 남고, 수정 전/후를 항목 단위로 맞출 수 있다.
- 항목마다 `edited` 여부를 둔다. 사용자가 채운 분량은 근거 없이 저장되므로 스키마에 `user_entered` 같은 상태가 필요하다. [#3 대기]
- 항목 단위 되돌리기: 사용자 레시피의 항목을 추출 결과의 같은 ID 항목으로 되돌린다.
- 근거 구간의 종류·원문·시각은 추출 결과에 내부 보관한다. MVP 화면의 근거 표시를 위한 API·UI 구현은 요구하지 않는다.
- 사용자별 접근 권한은 DB 행 단위로 강제하고 pgTAP으로 검증한다.

### 정답 데이터·평가·파인튜닝 루프 (선규)

- **학습 예제 = (evidence bundle, 정답 레시피 JSON).** 수빈과 선규의 경계는 evidence bundle 스키마다.
- **정답 만들기:** 강한 모델이 초안을 만들고 사람이 영상을 보며 고친다. [라벨링 가이드](labeling-guide.md)를 따른다.
- **데이터 분할:** 영상 단위로 학습·평가를 나눈다. 평가셋은 고정하고 학습에 절대 쓰지 않는다.
- **지표:** 재료 재현율·정밀도, 분량 정확도, 근거 없는 분량(지어낸 값) 수, 조리 순서 누락, 스키마 통과율. 근거 위치 정확도는 구간 ID가 아니라 **시각 구간 겹침**으로 계산한다(파이프라인 개선으로 구간 ID가 바뀌어도 비교 가능하도록). 재현율은 "전체"와 "근거가 있는 재료만"으로 나눠 1~4단계 개선 효과와 5단계 개선 효과를 분리한다. [#3 대기]
- **출처별 집계:** 평가셋 정답에서 재료가 어느 출처(설명·고정 댓글·말소리·화면 글자)로 확인되는지 비율을 낸다. 3주차 개선 방향(음성 vs OCR)을 정하는 근거로 쓴다.
- **파인튜닝 방식:** 1주차에 비용·데이터 반출 조건을 보고 정한다. 후보는 API 파인튜닝과 오픈 모델 LoRA다. 정답 데이터가 적을 때는 프롬프트 개선과 비교해 실제로 나아졌는지 확인한다.
- **사용자 수정본:** 항목 단위 수정 전/후 쌍을 검토를 거쳐 학습 데이터 후보로 쓴다.
- **비교 세트:** 평가셋과 별도로 경쟁 서비스 비교용 영상을 둔다. 구성과 방법은 [경쟁 서비스 비교](<competitors.md#비교-실험-계획>)를 따른다.
- **수집과 추출을 분리 평가:** 수집 성공률과 레시피 정확도를 따로 집계한다. 시각 없는 출처는 시각 평가에서 분리하고 시간 있는 근거 비율을 함께 보고한다. 캡션만 확보한 사례를 영상 전체 분석 사례와 같은 조건으로 비교하지 않는다.

### 화면 (유란)

MVP 흐름은 **링크 입력 → 레시피 확인·수정 → 저장 → 내 레시피북**으로 한다. [기획안](plan.md)·[경쟁 서비스 비교](competitors.md)의 우리 대응도 같은 범위로 맞춘다. 기존 UX 원문의 항목별 근거·시각 이동 요구는 후속 PR #9에서 정리하며, #9는 이 화면 범위가 합의된 뒤 병합한다.

- 결과 화면에는 요리명·재료·원문 분량·조리 순서를 표시하고, 확인되지 않은 분량은 빈칸으로 둔다.
- 항목별 근거 버튼·원문·출처·시각 이동 UI와 신뢰도 요약은 제공하지 않는다. 근거·시각·검증 상태는 내부 검증·평가용으로 유지한다.
- 실패 안내는 `error_code`에 따라 다시 시도 / 파일 업로드 / 다른 영상 / 찾은 만큼 보기로 구분한다.
- 처리 단계는 `jobs.stage`를 표시한다.
- 캡션만 확보한 결과에는 결과 전체에 짧게 "설명 기반"이라고 안내한다. 항목마다 출처를 표시하지 않는다.
- 수정 화면은 항목 ID를 유지한 채 편집하고, 고친 항목은 "직접 입력", 항목별 되돌리기를 제공한다.

## 검증·범위 조절

- 사용성 가설은 간결한 확인·수정·저장 흐름이 저장 전 수정 부담을 줄이는지다. 화면 근거 표시의 효과는 이번 MVP에서 검증하지 않는다. 영상 재확인 횟수는 참고 지표로만 기록하며, 근거 표시 효과나 인과적 개선으로 해석하지 않는다.

- 매주 평가셋 점수를 갱신하고 이전 점수와 비교한다. 점수가 떨어지는 변경은 이유를 적고 병합한다.
- 평가셋 영상으로 과적합하지 않도록 평가셋 결과를 보고 프롬프트·데이터를 직접 고치지 않는다. 오류 분석은 별도 개발용 영상으로 한다.
- 경쟁 서비스는 일반 사용자로만 쓴다. 내부 API 호출, 이용 제한 우회, 자동화된 대량 제출은 하지 않는다.
- 지연 시 줄이는 순서: Instagram 수집기 → 내부 출처 충돌 처리 → 화면 장식 → 지원 입력 범위. 링크 → 레시피 → 레시피북 흐름과 평가 비교는 끝까지 유지한다.
- 11/20 이후 새 기능은 넣지 않는다.
- Instagram 수집이 불안정하면 후보 탐색을 무기한 늘리지 않고 캡션 제한 지원 또는 미지원으로 범위를 확정한다. YouTube·업로드·근거 검증·평가 흐름은 유지한다.
