# 평가셋 선정 기준 v0.1

수정일: 2026-10-28 · 팀 검토용 (KAN-10)
관련 문서: [기획안](<plan.md#차별화-가설과-검증>) · [개발 계획](<dev-plan.md#정답-데이터평가파인튜닝-루프-선규>) · [라벨링 가이드](labeling-guide.md) · [경쟁 서비스 비교](<competitors.md#비교-실험-계획>)

> **정답 형식은 #3 스키마 v0.2 안 기준이다. v0.2 합의 결과에 따라 바뀔 수 있다.** [v0.2 합의 전]

평가셋은 기본 버전과 파인튜닝 버전을 같은 조건으로 비교하는 기준이다. 한 번 고정하면 바꾸지 않으므로, 모으기 전에 고르는 기준·수집 확인·분담·고정 절차를 정한다. 팀원 3명이 10개씩 모아 30개를 만든다(KAN-40 수빈·KAN-41 선규·KAN-42 유란, 11/3). 수집 가능 여부 확인(KAN-18)과 같은 표를 쓴다.

각 항목은 **제안**·이유·대안 순서로 적는다.

## 1. 대상

**제안:** 한국어 요리 YouTube Shorts, 길이 3분 이하, 공개 영상만. 일부 공개·비공개·연령 제한·회원 전용 영상은 제외한다.

- 이유: 서비스가 받는 입력과 같은 조건이다. Shorts 길이 상한이 3분이다.
- 대안: 60초 이하만 → 표본이 좁아지고 긴 레시피 Shorts를 평가하지 못한다.

## 2. 근거 구성

영상을 **분량이 나오는 곳**으로 분류한다. 목표는 아래와 같고 각 ±1까지 허용한다.

| 분류 | 목표 |
|---|---|
| 말소리 | 8 |
| 설명란 | 6 |
| 작성자 고정 댓글 | 6 |
| 화면 글자 | 4 |
| 섞임 | 6 |
| 합계 | 30 |

- 이유: 평가셋 정답의 출처별 집계로 3주차 개선 방향(음성 vs OCR)을 정한다. 출처마다 최소한의 사례가 있어야 비교가 된다. PR #23에서 개발용 영상 6개 중 4개가 재료를 작성자 고정 댓글에 적어 둔 것을 보고 고정 댓글 몫을 따로 뒀다.
- 대안: KAN-18에서 확인한 실제 분포를 그대로 따름 → 드문 출처가 1~2개뿐이면 출처 비교가 약해진다.

### 분류 판정 규칙

1. 분량이 있는 재료마다 그 분량이 나온 출처(말소리·설명란·고정 댓글·화면 글자)를 모두 적는다.
2. 출처별 비율 = 그 출처에 분량이 나온 재료 수 ÷ 분량이 있는 재료 수.
3. 가장 높은 출처가 **70% 이상**이고 다른 출처가 모두 70% 미만이면 그 출처로 분류한다.
4. 그 밖(어느 출처도 70% 미만, 또는 두 출처 이상이 70% 이상으로 겹침)은 **섞임**.
5. 분량이 있는 재료가 2개 미만이면 재료 이름이 나온 곳으로 같은 규칙을 적용한다.

후보 단계에서는 영상을 보고 판정한다. 정답을 만든 뒤 정답으로 다시 계산하고, 달라지면 고정 전에 표를 고친다.

- 대안: 출처 우선순위로 재료마다 한 출처만 배정 → 우선순위(#3 G)가 아직 합의 전이라 보류.

예시(가짜 영상 `Smpl0Gochu1`): 분량 있는 재료 5개 중 고정 댓글에 5개, 말소리에 2개 → 고정 댓글 100%, 말소리 40% → **고정 댓글**.

### 화면 글자 분량 영상: 4~6개

**화면 글자로만 나온 분량이 1개 이상 있는 영상**을 4~6개 목표로 한다. 분류와 별도로 표의 "화면 글자로만 나온 분량 재료 수" 열로 센다.

- 하한 4: 1인 1개 이상. 출처별 집계에서 화면 글자 비중을 판단할 최소한의 사례가 필요하다.
- 상한 6(전체의 20%): 아직 OCR이 없어 이 분량은 bundle에 근거가 없다. 라벨링 가이드상 정답에서 `unconfirmed`가 된다. 이런 영상이 많으면 기본 점수가 "OCR 없음" 때문에 깎여 모델 오류와 구분이 어렵고, 아래 열린 문제의 영향도 커진다.

**열린 문제:** 정답 bundle은 라벨링한 때 그대로 고정한다(#3 F). 그러면 나중에 OCR을 붙여 화면 글자 분량을 맞혀도 정답은 `unconfirmed`로 남는다. 처리 방식은 평가 스크립트에서 정한다. 그때까지 화면 글자 분량 영상의 점수는 따로 보고한다.

### 지어낸 분량 측정용

분량이 어디에도 나오지 않는 재료가 있는 영상을 **3개 이상** 넣는다. 근거 없는 분량을 만드는지 보려는 것이다.

## 3. 다양성

**제안:**

- 요리 종류 6개, 종류마다 3~8개: 밥·덮밥 / 면 / 반찬·볶음 / 국·찌개 / 디저트·음료 / 간식·소스·기타
- 채널당 최대 2개
- 재료 수 3~20개. 재료 5개 이하 영상 5개 이상, 13개 이상 영상 3개 이상

- 이유: 한 채널·한 형식에 점수가 끌려가지 않게 한다. 재료 수가 많은 영상에서 누락이 잘 생기므로 따로 확보한다.
- 대안: 채널당 1개 → 30개 채널을 찾기 어렵고 수집 기간 안에 끝내기 힘들다.

## 4. 빼는 것

**제안:** 아래 영상은 평가셋에 넣지 않는다.

- 개발용 영상: 정답을 만든 개발용 5개, PR #23의 개발용 6개
- 경쟁 서비스 비교 세트, Instagram 사전 검증 세트
- 요리 영상이 아닌 것(먹방·리뷰·광고 위주)
- 자막과 설명란이 모두 없는 영상
- 레시피가 외부 링크(블로그 등)에만 있는 영상

**실패 사례는 평가셋 밖 별도 "실패 세트"(5개 내외)로 둔다.** `not_a_recipe`, 열 수 없는 영상, 정보 부족(`insufficient`) 사례로 `error_code`·`reason`이 맞게 나오는지만 확인한다. 정확도 점수에는 넣지 않는다.

- 이유: 정확도 점수와 실패 처리 결과를 섞으면 점수 해석이 어려워진다.
- 대안: 평가셋에 실패 사례 2~3개 포함 → 정답 레시피가 없어 지표 계산이 복잡해진다.

## 5. 분할 규칙

**제안:**

- 분할 단위는 영상이다([라벨링 가이드](labeling-guide.md) 5번).
- 평가셋은 학습·프롬프트 수정·오류 분석에 쓰지 않는다. 오류 분석은 개발용 영상으로 한다.
- **평가셋에 들어간 채널은 학습셋·개발용 영상에 쓰지 않는다.** 평가셋 채널 목록은 후보 표에서 뽑아 학습 데이터 수집 때 대조한다.

- 이유: 같은 채널은 고정 댓글·설명란·자막 형식이 비슷하다. 그 채널로 학습하면 평가셋 점수가 형식을 외운 만큼 올라 파인튜닝 개선이 부풀려진다.
- 대안: 채널 겹침을 허용하고 겹친 영상 점수를 따로 보고 → 학습 데이터는 모으기 쉽지만 발표 비교가 덜 깔끔하다.

## 6. 수집 확인

**제안:** 후보마다 자막 유무·자동 자막 여부·설명란·작성자 고정 댓글 확보 여부를 [후보 기록 표](#부록-후보-기록-표)에 적는다. KAN-18과 같은 팀 공용 시트를 쓴다.

- 후보 단계에서는 브라우저로 영상 페이지를 열어 눈으로 확인한다. 고정 댓글은 **작성자가 직접 쓰고 고정한 댓글**만 센다. 시청자 댓글은 고정돼 있어도 세지 않는다.
- 도구로 확인한 수집 결과는 [정답 작성 순서](#정답-작성교차-확인-순서) 1단계에서 만든다.

## 7. 나누기

**제안:** 1인 10개. 분류별 목표:

| 담당 | 말소리 | 설명란 | 고정 댓글 | 화면 글자 | 섞임 | 합 |
|---|---|---|---|---|---|---|
| 수빈 (KAN-40) | 3 | 2 | 2 | 1 | 2 | 10 |
| 선규 (KAN-41) | 3 | 2 | 2 | 1 | 2 | 10 |
| 유란 (KAN-42) | 2 | 2 | 2 | 2 | 2 | 10 |
| 합계 | 8 | 6 | 6 | 4 | 6 | 30 |

- 1인당 요리 종류 4가지 이상.
- 목표를 못 채운 분류는 표에 적고 다른 사람과 맞바꾼다.
- **겹침 확인:**
  - 영상 ID 열에 중복 표시(스프레드시트 조건부 서식)를 건다.
  - 후보를 넣기 전에 채널 열을 검색한다(채널당 최대 2개, 다른 사람 후보와 합산).
  - "제외 목록" 탭(개발용·비교 세트·Instagram 세트 영상 ID와 채널)과 대조한다.

- 이유: 분류를 나눠 맡아야 한 사람이 쉬운 영상만 모으는 일을 막는다.
- 대안: 분류 구분 없이 각자 10개 → 마지막에 분류가 모자라면 다시 찾아야 한다.

## 8. 고정

**제안:**

| 날짜 | 할 일 |
|---|---|
| 10/31 | 후보 30개 확정(표 상태 "후보" → 정답 작성 시작) |
| 11/3 | 정답·교차 확인 완료 → **평가셋 v1.0 고정** |

- 10/31 후보 확정 때 실제 분포를 보고 [2번 분류 목표](#2-근거-구성)를 ±2까지 조정한다. 조정한 값은 이 문서에 적는다.
- 고정할 것: 영상 목록, 영상별 수집 파일(`source.json`)·`bundle.json`·`recipe.json`. 자막 원문이 들어가므로 **레포 밖 비공개 저장소**에 둔다.
- 고정 뒤 영상을 바꾸지 않는다.
- 영상이 삭제·비공개되면 고정한 bundle로 5단계(구조화) 평가는 계속한다. 전체 파이프라인 평가에서는 빼고 빠진 개수를 함께 보고한다.
- **정답 오류:** 이슈로 올림 → 팀 합의 → 버전을 올림(v1.1) → 변경 기록을 남김. 기본 버전과 파인튜닝 버전 점수는 항상 같은 평가셋 버전으로 다시 계산해 비교한다. 평가 결과를 보고 정답을 고치는 것은 오류가 확인된 경우만이다([라벨링 가이드](labeling-guide.md) 5번).

- 이유: 발표 비교가 같은 기준 위에서 이뤄져야 한다.
- 대안: 삭제된 영상을 새 영상으로 교체 → 교체 전후 점수를 비교할 수 없게 된다.

## 정답 작성·교차 확인 순서

1. **수집 파일 고정.** PR #23 병합 뒤 아래 명령으로 자막·설명란·작성자 고정 댓글을 받아 파일 하나로 저장하고 고정한다. LLM을 부르지 않는다.
   ```bash
   cd pipeline
   node src/cli.mjs Smpl0Gochu1 --captions-only --out <정답 폴더>/E-01/source.json
   ```
   - #23·#24 병합 뒤 **자막 없는 개발용 영상 1개로 수집을 먼저 확인**한다(자막 없음이 오류 없이 넘어가고 설명란·고정 댓글이 남는지).
2. **bundle과 초안 만들기.** 고정한 파일로 bundle과 초안 recipe를 만든다. bundle의 근거 구간은 수집 파일에서 그대로 나오므로 다시 돌려도 같다.
   ```bash
   LLM_PROVIDER=anthropic LLM_MODEL=claude-opus-5-5 \
     node src/cli.mjs --transcript <정답 폴더>/E-01/source.json --team-out <정답 폴더>/E-01
   ```
   - **유료 LLM 호출이다.** 30개 실행 전 팀에 횟수·예상 비용을 알리고 확인받는다.
   - 초안 모델은 **평가 대상(gpt-4.1·프롬프트 v7)과 다른 모델**을 쓴다. 평가 대상과 같은 모델의 초안을 사람이 덜 고치면 정답이 그 모델 쪽으로 기울어 기본 점수가 부풀려진다. 쓴 모델·프롬프트 버전을 표에 적는다.
   - 비용: 모델 단가는 실행 전 확인한다. 실제 비용은 실행 결과의 `usage`로 기록한다.
   - 파이프라인의 Anthropic 호출은 `max_tokens: 4096`이라 출력이 잘릴 수 있다. 30개를 돌리기 전에 **개발용 영상 1개로 먼저** 확인하고, 잘리면 수빈에게 공유한다.
   - 지금 CLI에는 LLM 없이 bundle만 만드는 옵션이 없다.
3. **수정.** [라벨링 가이드](labeling-guide.md)대로 영상을 처음부터 끝까지 보며 초안을 고친다. bundle은 고치지 않는다.
4. **검사.** `python scripts/validate.py <정답 폴더>/E-01`. v0.2 형식 검사는 스키마 PR 병합 뒤 가능하다.
5. **교차 확인.** 다른 팀원 1명이 확인한다. 순환: 수빈 → 선규 → 유란 → 수빈(수빈이 만든 정답은 선규가 확인).
6. 표 상태를 "확정"으로 바꾸고 [2번 분류](#분류-판정-규칙)를 정답으로 다시 계산한다.

### 정답 형식 [v0.2 합의 전 — 바뀔 수 있음]

- `schema_version: "0.2"`, 재료·단계 `id` 필수(`ing-1`, `step-1`).
- 근거 종류: `title`·`description`·`comment`·`asr`·`ocr`. `asr`·`ocr`만 시각이 있다.
- 정답에는 `partial`·`edited`·`user_entered`를 쓰지 않는다.
- 기존 v0.1 정답(개발용 5개)은 #3 H의 이전 스크립트(스키마 PR에서 추가 예정)로 변환한다.
- 재현율은 평가 스크립트에서 "전체 / 근거 있는 재료만"으로 나눠 낸다(스키마 변경 없음).

### 정답 작성 전에 정해야 할 것

## 부록: 후보 기록 표

**둘 곳:** 팀 드라이브 비공개 공용 시트(평가셋 후보 + KAN-18 수집 확인). 영상 ID·링크가 들어가므로 **레포에 두지 않는다.** 이 문서에는 열 이름만 적는다.

KAN-18 수집 가능 여부 확인도 이 시트에 함께 기록한다.

**필수 (13)**

| 열 | 값 |
|---|---|
| 후보 번호 | `E-01` … |
| 담당 | 수빈 / 선규 / 유란 |
| 영상 ID | 예: `Smpl0Gochu1` |
| 채널 | 채널 이름 |
| 길이(초) | 숫자 |
| 요리 종류 | 3번의 6개 중 하나 |
| 자막 | 없음 / 자동 / 수동 |
| 설명란 레시피 | 없음 / 재료만 / 재료+분량 |
| 고정 댓글 레시피 | 없음 / 재료만 / 재료+분량 (작성자 고정 댓글만) |
| 화면 글자 레시피 | 없음 / 재료만 / 재료+분량 |
| 분량 출처 분류 | 말소리 / 설명란 / 고정 댓글 / 화면 글자 / 섞임 |
| 초안 모델·프롬프트 | 예: `claude-opus-5-5 / recipe-extract-v7` |
| 상태 | 후보 / 확정 / 제외: 사유 |

**선택:** 링크 · 요리 이름 · 재료 수 · 자막 언어 · 화면 글자로만 나온 분량 재료 수 · 분량 없는 재료 유무 · 확인일 · 정답 작성자 · 교차 확인자 · 메모

**탭:** 후보(위 표) · 제외 목록(개발용·비교 세트·Instagram 세트) · 실패 세트
